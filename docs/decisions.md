# Architecture Decisions

Log of approved deviations from `docs/architecture.md`. When a phase reveals a real
gap in the doc, fix the doc first, then append one line here — see the "When
Things Go Wrong" section of `docs/build-playbook.md`.

Format: `YYYY-MM-DD — <what changed> — <why>`

---

2026-10-23 — **The admin features are a second employee agent, `AMF_Matrix_Admin_Assistant`, for administrators only** (§7, §11; technical log M15) — the user's choice, over admin-only actions inside the submitters' assistant. Its access permission set is `org-config/amf-dev`'s and assigned to administrators; its three actions are granted by `Approval_Matrix_Admin` alone. Submitters never meet admin features, and neither agent's routing has to tell the two audiences apart.

2026-10-23 — **Principle 6 extended: AI may draft a rule, but a draft routes nothing** (§1, §9; technical log M15). A model-drafted rule is shown only once Apex has run the release gate's checks on it (compile, a free priority, an active process, the engine's union query, the metadata's own limits), with one corrected attempt and then a plain refusal. A valid draft is a Custom Metadata file for the administrator to commit and release through the ordinary gate (principle 1); the assistant cannot deploy or activate anything.

2026-10-23 — **The engine gains `previewEach()`, and the impact check compares two engine runs** (§6.4, §7; technical log M15) — the user's choice of engine entries, over previewing one record per call. The same recently decided records (the last 90 days, at most 200) are previewed under the live matrix and under `AMF_DraftRuleProvider`'s changed one, on their values today: a decision log row records only what the deciding rule read, so a changed rule cannot be replayed against the recorded values. A record the engine refuses on either side is counted as skipped. A replacement must carry a new version, because `AMF_ExprCache` keys on DeveloperName and version.

2026-10-23 — **A health report's figures are Apex's, and the summary is optional** (§7, §8; technical log M15). Every number is counted from the decision log and the pending approvals into plain-text facts, and the template is given those facts alone. If Einstein cannot summarise them, the facts are still the report.

2026-10-23 — **The admin agent's instructions say what the model does not know, and its tools are named as lookups** (§1 principle 6, §7; technical log M15.3). In the gate's live sessions the model answered without calling its tool: in 7 of 7 sessions it wrote a draft rule itself, with an invented file path and condition, even when asked by name to use the tool; and in a session already under way it invented impact and health figures ("1,242 decisions" against 29). The traces showed the tools offered every time and no FunctionStep. Each fabrication followed the answer's shape the instructions described. The platform's own preamble tells the model to use tools for "new information", and drafting reads to it as writing, not looking up. Telling it plainly that it does not know the object's fields, rules, processes, records or counts, and that only the tool does, together with tool names such as get_checked_draft and get_health_report and no answer templates, gave 9 of 9 calls in fresh and running sessions and 18/18 Testing Center assertions twice. Renaming the inputs and outputs that might collide with script keywords did not change it, though the new names were kept.

2026-10-23 — **A drafted rule's name is checked against the active matrix only** (§9; technical log M15). `AMF_RuleProvider` exposes active rules, and `CLAUDE.md` allows Custom Metadata to be read only through it, so an inactive rule's name is invisible to the drafter. Releasing a draft with such a name would overwrite that inactive record; the draft's file name shows it in review. Widening the provider interface was left to a later phase.

2026-10-23 — **The current approver of a pending approval may read that approval's decision log row** (§8, §11; technical log M14) — the user's choice, over keeping the reason hidden or showing it in the briefing alone. It supersedes the 2026-10-08 entry below for that case only. The person deciding is the one who most needs to know why the matrix sent the request to them, and a briefing that could say why while the timeline said "not visible" would contradict itself. The row is read without sharing, bound to the one approval waiting on the reader, and only while it waits; no record is shared and the log stays Private. "Waiting on the reader" is `AMF_ApproverScope`'s single definition: the assigned user, members of the assigned queue or group (nested groups to depth 5), and the assigned user's delegated approver. Role-based queue members are not followed, because the templates name users, queues and groups only.

2026-10-23 — **The engine gains `previewWith()`, a write-nothing what-if** (§6.4; technical log M14) — the user's choice, over answering a what-if outside the engine. A second evaluator walk would be a second place for the route to drift from the one a submission takes; changing values on the in-memory copy after step 4 keeps rule order, compilation and first-match the engine's. Only the record's own fields may change, and they are checked after authorisation, so the refusals match `preview()`'s. `submit()`, `preview()` and `submitEach()` reach the same private overload with no changes and are untouched.

2026-10-23 — **A what-if clears `can_submit`** (§7; technical log M14). Submit's record and expected process are bound to the last preview, and a what-if is not one. Clearing the flag means "submit it" after a what-if always starts from a fresh preview of the record's real values, so nobody submits believing the values they tried were used.

2026-10-23 — **A briefing belongs to the assistant's explain subagent; `my_work` holds the two lists** (§7; technical log M14.3). The first design put briefings in `my_work`. In Testing Center the published agent sent "Brief me on the approval for PR-00000045" to the explain subagent in five runs out of six, whatever the router's instructions said, while the local preview of the same bundle routed it as instructed. The published runtime chooses largely by the subagents' descriptions, and a briefing is an explanation written for the approver: same facts, same template. Putting it where the platform sends it made routing stable (42/42 assertions in two consecutive runs), and `my_work` keeps the action only for an approval from a list it has just given.

2026-10-23 — **A reassigned approval step is described by whom it went to** (§8; technical log M14.3). Measured in `amf-dev`: a `Reassigned` history row's ActorId is the new assignee and its OriginalActorId the step's first assignee, whoever made the change; the person who reassigned it is not recorded. M13's facts said "reassigned by X, for Y", and the model read that as X handing the step to Y, the wrong way round. The facts now say "reassigned to X (first assigned to Y)". The timeline LWC's own wording of such a row is carried, because M14 changes no LWC.

2026-10-23 — **The approver's briefing reuses the explanation template, asked the approver's question** (§8; technical log M14). It is the same facts with one line naming the reader as the approver it waits on, and a question that asks for what is asked, why it was routed there and what has happened, and says not to recommend a decision. A second template would be a second version to keep active (M13.7a) for no change in what the model may be told.

2026-10-23 — **The agent is published by `scripts/publish-agent.ps1`, not by `sf agent publish` run in the project** (§12 item 9; technical log M13.7b). The CLI looks for an authoring bundle only in the default package directory, `force-app`, and has no flag to look elsewhere. The script publishes from a throwaway project whose one default directory holds a copy of the bundle, with `--skip-retrieve`, then activates it. The alternatives each undid something decided earlier. Moving the bundle into `force-app` would end M13's portability. Making `agentforce` the default would weaken M12's source gate, which treats the default directory as the framework.

2026-10-23 — **The prompt template's source takes the retrieved form, naming its active version** (§8; technical log M13.7a) — as for M12's approval templates (2026-10-22, below). A template deployed without `activeVersionIdentifier` publishes its version but leaves none active, and Einstein refuses to run it. The source therefore carries the platform-assigned `versionIdentifier`, the active pointer to it, the platform's two defaults, and the content as the platform escapes it. A retrieve then matches the source byte for byte. New content makes a new version, which needs the same treatment.

2026-10-23 — **The agent's Testing Center definition is `org-config/amf-dev`'s** (§11; technical log M13.7f). `sf agent test create` writes it into `force-app`. But it names `amf-dev`'s records and needs the published agent, like the access permission set, so it moves beside that set. The YAML spec in `specs/` stays its source.

2026-10-23 — **AI sits around the engine, never inside it** (§1 principle 6, §7, §8; technical log M13) — the user's choice of the first two AI use cases, "submit by chat" and a plain-English "why", over AI routing or AI approval. A model choosing a route cannot be reproduced, and a log snapshot cannot explain its choice. A misroute is an audit finding (principles 3 and 4). So the agent's actions call the engine's own `preview()` and M10's `submitEach()`, which write exactly the row any other entry point writes. Explanations read a decision only after it is recorded. No model output is ever stored or acted on.

2026-10-23 — **The assistant is an employee agent written in Agent Script, and its submission is gated by the script, not by the model** (§7; technical log M13). Submit is offered only after a preview that reached a decision (`can_submit`). Its record and expected process are bound by the runtime to what was previewed, and the platform's confirmation runs before it does. Whether the route changed since the preview is compared in Apex. Agent Script over the older planner metadata, because its runtime-bound inputs and `available when` gates make those guarantees deterministic, and it is the authoring format the CLI publishes and tests. Lightning types for richer cards in the agent panel stay out: they could not be exercised in this session, and plain sentences built in Apex already carry every fact.

2026-10-23 — **Explanations are generated on demand from the timeline's view of one decision, and never stored** (§8, §11; technical log M13). The Flex template takes text built by `AMF_DecisionExplainer`, not a record it would ground itself. The timeline has already applied §8's two visibility rules, and a template that read the record or the log would need them again, in a second place. Not stored, because a generated sentence on the record would compete with the immutable row it paraphrases. The component puts an explanation away when the approval's history changes, rather than leave it describing a state that has passed.

2026-10-23 — **The AI metadata lives in its own package directory, `agentforce/`, and `sourceApiVersion` rises to 66.0** (§12 item 9; technical log M13). A prompt template or an authoring bundle deploys only to an org with Einstein generative AI and Agentforce on: `amf-dev` refused the bundle with "Not available for deploy for this organization" while Agentforce was off. Inside `force-app` they would end M12's promise that the framework deploys to any org. Agent Script needs Metadata API 66 or later. Apex classes stay at 62.0, so §12 item 6's API 67 user-mode change cannot reach the engine.

2026-10-23 — **The agent-access permission set is `org-config/amf-dev`'s, deployed after the agent is published** (§11; technical log M13). `agentAccesses` names the published Bot, which exists only after `sf agent publish`, so the set cannot deploy with `force-app` to a fresh org. Who may open the agent is also each org's own decision. The cost: in `amf-dev`, the first deploy of `org-config/amf-dev` waits for the first publish.

2026-10-23 — **`AMF_DecisionTimelineService` gains a public `describeValues()`** (§8; technical log M13) — an additive change to an M7 class, under M13's authorisation. The agent's preview describes values before any row records them. Sharing the timeline's own labelling means a route reads the same in the agent as on the record page, rather than through a second label resolver that could drift from the first.

2026-10-23 — **Approvers are named from `ActorId` when the approval was created in the same transaction** (§7; technical log M13). The platform returns `Actor.Name` as null on work items created in the running transaction, as the M8.7 actor-name fix found for history rows. `AMF_AgentSubmitRoute` reads the work items it has just caused, so it resolves each `ActorId` against User and Group (a queue). Otherwise the agent could never say who a new approval is waiting on.

2026-10-22 — **Released templates are fingerprinted in a committed manifest, `config/template-releases.json`** (§5.1, §9; technical log M12) — the user's choice, over a git diff against a release tag. The gate compares each template's SHA-256, taken without `<active>`, with insignificant whitespace dropped and line endings normalised. That is deterministic, works offline and in a shallow CI clone, and does not depend on branch history. Activation is excluded because superseding a template means deactivating it. Everything else, a description included, is released content. Releasing is one line, which the gate prints. Editing a fingerprint by hand defeats the check, and the manifest's description forbids it. Review is the only control on that.

2026-10-22 — **Committee steps are built on Classic now** (§5.2, §5.4; technical log M12) — the user's choice, over waiting for Flow's unanimous value (§12 item 1). It supersedes "queue or committee templates" on `CLAUDE.md`'s out-of-scope list. Classic cannot assign a step to a public group, so `PR_Finance_Committee` names `G_Finance_Approvers`' members as users. The group reaches `PR_Credit_Risk_Queue` as the queue's member, which a real-platform test shows works. A committee rule can move to Flow one row at a time once the value is known.

2026-10-22 — **The org's own configuration lives in its own package directory, `org-config/amf-dev`** (§6.3; technical log M12) — the user's choice, over stripping `amf-dev`'s fields from the layouts or keeping them in the package. Opportunity's four layouts and its object settings moved there unchanged. Stripped layouts deployed to another org would overwrite that org's pages, so standard objects' layouts are org configuration. `force-app` must hold none, and the gate fails one there. The cost: in another org, removing the standard Submit button from a governed standard object's layouts is that org's admin's step.

2026-10-22 — **Templates name users as `<alias>@{{AMF_USERNAME_DOMAIN}}`, filled at deploy from that environment variable** (§11; technical log M12). The handoff proposed a `sfdx-project.json` replacement. The placeholder, rather than `amf-dev`'s domain as the string replaced, means the source names no org. A forgotten variable then fails the deploy instead of shipping `amf-dev`'s usernames to another org. The cost: every deploy that includes approval processes needs the variable, `amf-dev`'s included, and `CLAUDE.md`'s deploy line says so. A retrieve writes real usernames back into source, and the gate refuses them.

2026-10-22 — **The source gate's guard checks cover every active template, not only those a rule names** (§9; technical log M12) — an extension under M12's authorisation. Once templates have versions, an active template that no rule names is a real state: a new version before its rules are repointed. If its entry criteria lacked the guard, a submission that bypassed the engine could enter it.

2026-10-22 — **The six templates' source takes the form a retrieve returns** (§5.1; technical log M12). On deploy, the platform drops `rejectBehavior` from a first step and appends `Owner` to a custom object's approval page fields. Released as authored, every template would read as edited in place after its next retrieve. The org already held these forms, so nothing deployed changed. A retrieve of all six, matched against the manifest, shows it, `PR_Three_Level_Finance`'s placeholder included.

2026-10-21 — **The source gate enforces §6.3's button removal on every layout of a governed object, and requires those layouts in source** (§6.3, §9; technical log M11) — an extension of the gate under M11's authorisation. Opportunity's four stock layouts listed the standard `Submit` button explicitly, and M3.9 showed that a deploy status cannot verify a claim about a UI. A layout with no explicit action list fails too, because the platform's default set includes the button once an approval process exists. So does a governed object with no layout in source, because a layout that exists only in the org cannot be checked. The cost: a standard object's layouts become source, and they reference that org's own fields, which ties the source to the org it was retrieved from (carried, with the templates' approver usernames).

2026-10-21 — **§4.4's 55-relationship limit corrected, and the validator runs each object's union query instead of counting** (§4.4, §9; technical log M11) — the user's choice, over dropping the check or counting against 55 anyway. M9.5 proposed counting against SOQL's documented limit of 55 child-to-parent relationships. In `amf-dev`, Apex at API 62 does not enforce it: one dynamic query joined 142 distinct relationships and returned its row. A count would have refused matrices the platform runs. Running the engine's own query against no records reports whatever the platform does refuse, and cannot be wrong about the platform.

2026-10-21 — **Opportunity is the second governed object, with both templates on the submitter's manager hierarchy** (§3.2, §5.2, §11; technical log M11) — the object is the user's choice, over a second custom object; it supersedes "second object" on `CLAUDE.md`'s out-of-scope list for Opportunity alone. The seeded approvers hold Salesforce Platform licenses, which grant no Opportunity access, and the org has one full license to spare, so a named-user template would need an approver it cannot provide. Hierarchy templates also name no user, so they deploy to any org. Neither template locks the record after final approval, because an approved deal must stay editable. The rules exercise a standard relationship (`Account.Industry`) and M9's `IN`.

2026-10-21 — **M10.7's real-platform guard tests use a test-only validation rule, not the approval lock** (technical log M10.8) — the user's choice, over rewriting the tests to pin what the org did or deleting them. M10's org gate showed that, under `System.runAs` of a non-admin, the lock a final approval leaves did not stop the engine's guard update, so the fixture could not make step 9 fail. `AMF_Test_Refuse_Guard`, a validation rule on `Purchase_Request__c` with a custom permission of the same name that no permission set grants, refuses the guard on a Strategic-vendor request to the permission's holder. It gives a real `FIELD_CUSTOM_VALIDATION_EXCEPTION` in every org and is inert for every real user. It is the first metadata the repo ships only for a test, and it lives on the framework's own pilot object, never on an adopter's. The entry below no longer counts the lock as a case the engine meets: whether it stops a real non-admin outside a test is unmeasured.

2026-10-21 — **Step 9 stages the guard record by record** (§6.1, M10.3b; technical log M10.7) — the user's go-ahead for the follow-up M10 carried, under M10's authorisation. A record whose `Matrix_Submission__c` the platform will not set (a validation rule it fails, or the lock a final approval leaves) is a `Failed` row carrying the platform's reason and is not submitted; the other records go ahead. The header button gets the same answer in place of an exception, as it has for a platform refusal since M10: the matrix decided, so the attempt is logged. Re-arming a refused record stays all-or-nothing, because a record left with its guard set and in no process is the bypass §6.3 closes, and failing the call is the safe answer.

2026-10-08 — **Bulk entry points answer per record; the header button keeps its whole-call contract** — the user's choice. `submitEach()` gives an unreadable, already-pending, platform-refused or ungovernable record its own outcome (`Refused` or `Failed`) and lets the rest through, because one bad record must not fail a 200-record Flow. `submit()` and `preview()` keep refusing the whole call (the 2026-08-18 and 2026-10-08 entries below still hold for them), because the UI submits one record and its messages and tests are built on that contract. `Refused` is an outcome, not an `Outcome__c` value: nothing was decided, so nothing is logged.

2026-10-08 — §6.1's step order changes: **the decision log is written after the platform answers** (step 10 before step 8, with step 11 folded in), and the Classic strategy submits **without all-or-nothing**. A platform refusal is now a `Failed` row carrying the platform's reason, with the record's guard re-armed, instead of a rollback that also erased every other record's row (M3.8's carried bulk item). Through the header button this changes one thing: a platform refusal there now leaves a `Failed` row. `AMF_DecisionLogWriter.stamp()` is retired with step 11; `Lock_Decision_Log` still permits the one post-insert stamp, which nothing performs any more (technical log M10.6).

2026-10-08 — **`TODAY` stays the running user's date** for Flow and REST submissions — the user's choice over the org's time zone. One rule serves every entry point, and every row records the date it used, so an integration user's time zone shows in the log rather than hiding in a setting.

2026-10-08 — **A record Id twice in one call:** `submit()` refuses it, because submitting it twice would see the second refused by the platform and the guard of a pending record re-armed; `submitEach()` submits it once and gives every request the same answer. The REST call takes at most 200 records, the size tested in one transaction.

2026-10-08 — **A broken relationship path is *unknown*, under three-valued (Kleene) logic, not false** (§4.3, M9 note) — extends the 2026-08-18 entry below. "False" sufficed while expressions could only `&&` and `||` a comparison; `NOT` would turn it into a match (`NOT (Account__r.Name == NULL)` true for a record with no Account), the very presence check that entry forbids. `AND`/`OR`/`NOT` now treat it as SQL treats unknown, and a rule matches only on a definite true. No pre-M9 expression changes its result; a null *leaf* stays two-valued.

2026-10-08 — §4.1's **"NOT binds tightest, then comparisons" is read through its productions**: `NOT`'s operand is a `unary_expr`, so `NOT a == b && c` is `(NOT (a == b)) && c`. The prose's literal reading, `(NOT a) == b`, would apply `NOT` to a non-Boolean.

2026-10-08 — **`NULL` is refused in an `IN` comparison, in the list and as its operand** (§4.3, M9 note) — otherwise `Field__c IN ('A', NULL)` would be true for a blank field, contradicting §4.3's "`IN` with a null operand is false". `IN` is accepted for every single-valued type, not only the text types §4.3's table names, because it is defined as `==` against any one value.

2026-10-08 — **Multipicklists compare only with a `;`-separated text literal** (§4.3, M9 note): `==`/`!=` an exact set match in any order and case, `CONTAINS` membership of every listed value. Field-to-field, `IN`, `STARTS_WITH` and ordering on a multipicklist are refused, and a literal naming no values is a compile error — §4.3 defines none of them, and a guess would be a silent mis-route.

2026-10-08 — **`TODAY` is recorded in `Evaluated_Values__c` under the key `TODAY`** (§3.3, §4.3 M9 note) — a decision that depended on the date must say which date; `Submitted_At__c` alone cannot, because `TODAY` is the submitter's local date and their time zone is not recorded. `TODAY` is a reserved word, so the key cannot collide with a field path; the timeline and the preview show it as recorded.

2026-10-08 — §4.4's **path cap is four segments (three hops), and "platform limit" was wrong** — §4.1's "max 4 hops" is read in §13.3's unit, where `Account__r.Region__c` is two hops; SOQL itself allows five relationship hops (six segments), measured in `amf-dev`. One constant, `AMF_ExprCompiler.MAX_PATH_SEGMENTS`, now shared by the resolver, raises it.

2026-10-08 — **Supersedes the 2026-08-18 word-forms entry below:** `AND`, `OR` and `NOT` are accepted alongside `&&`, `||` and `!`, as §4.1 specifies — M9 authorised the full grammar, and the entry's own premise was that enabling them was "two entries and no parser change".

2026-10-08 — §5.2 **corrected: recall actions re-arm the guard too.** It named only the final approval and rejection actions, and both templates were built to it, so a recalled request kept `Matrix_Submission__c = true` and a submission bypassing the engine passed entry criteria unlogged (technical log M7.8). Both templates now clear the guard on recall, and the source gate fails any template that does not clear it on all three ways out of a process.

2026-10-08 — A **record already in an approval process is refused for the whole call, before step 1, with no decision log row** (§6.1, M8 note) — chosen by the user over a new `Outcome__c` value: nothing was decided, as with a record the caller cannot read, and a new value would change a restricted picklist that the lock rule and every report rely on. The check runs after authorisation, so it reveals nothing about a record the caller cannot read. Like the read-access check it condemns the whole call; per-record handling belongs with bulk entry points, if they are built.

2026-10-08 — §8's timeline names the matched rule by its **DeveloperName and version**, not by its description as §8's example sentence does ("Matched **High-value APAC** v3") — the log snapshots only `Matched_Rule__c`, and reading today's description from the live matrix into a past decision would let a later edit rewrite the explanation of an earlier one, which is the flaw §8 exists to fix; `Approval_Matrix_User` cannot read the matrix either (§11). Showing descriptions would take a new snapshot field on the log, not a timeline change.

2026-10-08 — The timeline shows **native approval history to anyone who can read the record, and a decision log row only to those who can read that row** — §11 gives `Approval_Matrix_User` its own rows, and the native half follows the rule the Approval History related list already applies. An approver therefore sees every approval and its steps, but the routing reason only for submissions whose row they can read; any other approval is shown and labelled as unexplained, not hidden. Letting approvers read the reason would be a sharing decision for `Approval_Decision_Log__c`, not a timeline change.

2026-10-07 — §5.3, §5.4, §12 and Appendix A **corrected to the M6 Flow spike's findings** (`docs/spike-results.md`, Round 2): the Flow template contract at API 67 (four inputs, `runInMode`, `stepBackground`, username approvers), the launch call confirmed as `Flow.Interview…start()` with a synchronous `ApprovalSubmission`, rejection not stopping later stages, recall running the recall path while cancel does not, and Apex API 67's user-mode default — because the platform moved between Round 1 (API 62) and Round 2, and §5.3 stated facts that no longer hold. No design decision changes: the Flow strategy remains unbuilt and out of scope, and unanimous group semantics remain open.

2026-09-18 — §9's configuration validator is a **source gate plus a required
post-deploy Apex gate**, not a literal metadata-deploy hook: Salesforce deploys cannot execute
Apex. `scripts/validate-approval-matrix-source.ps1` checks the source template's active state
and exact `Matrix_Submission__c = TRUE` entry criterion; `AMF_ConfigValidator` checks the
deployed active rules, expression compilation, duplicate priorities, Checkbox guard and active
Classic `ProcessDefinition` target. This split is necessary because `ProcessDefinition` exposes
no entry-criteria field to Apex SOQL. The post-deploy script throws on findings, making CI fail
before the new configuration is accepted.

2026-08-18 — §6.1 step 6's "throw a clear error" is implemented as a **per-record blocked Outcome**, not an exception; `AMF_ApprovalMatrixService.submit` throws only for faults condemning the whole call — nothing to submit, a mixed-object batch, a record the caller cannot read, an object with no active rules or no guard field, a rule that will not compile, a failed `Approval.process()`. The two halves of step 6 are mutually exclusive in Apex: an exception escaping the top of a request rolls back every DML before it, so throwing would erase the `Blocked_No_Match` row §3.3 exists to create. Catching it in every caller would preserve the row but make the audit trail depend on caller discipline, and would abort a batch at its first blocked record. This is not §4.6's forbidden catch-and-return-false — the evaluator still swallows nothing, the record still does not route, and the trace now outlives the transaction. Pinned by `AMF_ApprovalMatrixServiceTest.noMatchBlocksAndLeavesARowThatSurvivesTheTransaction`.

2026-08-18 — A rule that will **not compile blocks every record in the call**, rather than being skipped so lower-priority rules can still match — §4.6 at its sharpest, and the one place the MVP is stricter than a literal reading of §6.1. If the priority-10 rule cannot be evaluated, nobody can say a record would not have matched it, so letting the priority-20 rule pick it up is precisely the silent misrouting the framework exists to prevent. §9's config validator would move this to deploy time; §9 is out of MVP scope (§13.2), so it surfaces at submit. Pinned by `AMF_ApprovalMatrixServiceTest.aRuleThatWillNotCompileStopsEverythingRatherThanFallingThrough`.

2026-08-20 — §6.3's removal of the standard Submit for Approval button, and the placement of the framework's own action, are **both** `<platformActionList>` — not `<quickActionList>`. The standard button is the entry `Submit` / `StandardButton`; omitting it from `platformActionList` is the removal, and the platform re-adds it to the action bar whenever an approval process exists unless that list overrides it. An LWC quick action also **can** be deployed there, as `<actionType>QuickAction</actionType>`, though `quickActionList` refuses one outright ("You can't add QuickActionType LightningWebComponent to a QuickActionList", confirmed at API 62.0 and 64.0). The layout round-trips: retrieve and redeploy both preserve it.
